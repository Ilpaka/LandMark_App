# PERFORMANCE_REPORT.md — LandMark, этап 4

Цель этапа — показать **измерение**, а не оценку «на глаз». Использованы два подхода:
лёгкое измерение времени ответа через `curl` (без внешних зависимостей) и k6-скрипт
(`tests/load/basic_load.js`) для воспроизводимой нагрузки, если k6 установлен.

## 1. Измерение времени ответа API (curl)

Инструмент: `tests/load/perf_curl.sh`, 30 запросов на эндпоинт, метрика `time_total`.
Условия: локальный Docker demo-стенд, один хост. Полный вывод: `reports/perf_curl_summary.txt`.

| Эндпоинт | Код | min | avg | p95 | max |
|----------|-----|----:|----:|----:|----:|
| `GET /healthz` | 200 | 2.7 ms | **5.4 ms** | 7.1 ms | 23.5 ms |
| `GET /v1/places` (чтение из БД) | 200 | 4.1 ms | **7.9 ms** | 8.7 ms | 30.7 ms |
| `GET /v1/places/{uuid}` (not found) | 404 | 3.8 ms | **5.7 ms** | 7.1 ms | 8.3 ms |
| `POST /v1/auth/login` (неверный пароль) | 401 | 4.1 ms | **9.2 ms** | 23.0 ms | 26.0 ms |

**Выводы:**
1. Среднее время ответа API — **единицы миллисекунд** (avg 5–9 мс), p95 < 25 мс. Для локального стенда это хороший результат; узких мест на уровне API не выявлено.
2. Самый «тяжёлый» сценарий — `POST /login` (avg 9.2 мс): ожидаемо, так как выполняется проверка пароля (хэширование) — это нормально и работает как защита от перебора.
3. Первый запрос к каждому эндпоинту даёт пик (max до 30 мс) — холодный старт соединения/пулов; последующие стабильны.

## 2. k6 (нагрузочный скрипт)

Скрипт `tests/load/basic_load.js` проверяет `GET /healthz` и `GET /v1/places`
с порогами «status 200» и «время < 1000 мс». На этой машине **k6 не установлен**
(`k6: NO`), поэтому фактический прогон не выполнялся; скрипт приложен как готовый
артефакт. Запуск при наличии k6:

```
k6 run tests/load/basic_load.js
```

См. также `reports/k6_summary.txt` (пояснение + результат curl-замера как замена прогона k6).

## 3. Диагностика web-UI (Lighthouse)

Lighthouse выполнен против развёрнутого web-интерфейса стенда — Grafana
(`http://localhost:3000/login`), т.к. Flutter-фронтенд на этой машине не собирается.
Отчёт: `reports/lighthouse_report.html`.

| Категория | Оценка |
|-----------|-------:|
| Performance | **31** |
| Accessibility | **100** |
| Best Practices | **100** |
| SEO | 58 |

- Total Blocking Time ≈ 1170 мс, Cumulative Layout Shift = 0.
- Низкий Performance объясняется тем, что Grafana — тяжёлый JS-SPA (большой бандл, высокий TBT). Это характеристика стороннего UI мониторинга, а не бизнес-логики проекта. Связанный риск — см. `RISK_REGISTER.md` (медленная загрузка web-интерфейса).
